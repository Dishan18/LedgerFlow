LedgerFlow

A payments backend with a double-entry ledger, built with Java 21 and Spring Boot 4. Merchants take UPI-style payments through it; every rupee that moves is a balanced, append-only journal entry; every POST is idempotent; events reach merchants as signed webhooks; and the books are reconciled every night against the bank.

Java 21Spring Boot 4.1PostgreSQL 17 AWS SNS / SQS / S3ECS FargateTerraform Testcontainersjqwikk6GitHub Actions

The 30-second pitch

"LedgerFlow is a payments service like a tiny Razorpay. A merchant creates a payment, the service gets it authorized by a bank, and on capture it moves money through a double-entry ledger that the database itself keeps balanced. I built it to stay correct when things go wrong: 1,000 concurrent requests on one account, clients retrying the same request, a bank that times out or loses responses, and merchants whose servers are down. It has a transactional outbox to SNS and SQS for signed webhooks with retries and a dead-letter queue, and a nightly reconciliation against the bank's settlement file in S3. Under a k6 load test it sustained 175 payments a second with p99 under 200 ms and zero ledger imbalance, and reconciliation caught 100% of deliberately planted mistakes."

Six problems it solves

ProblemSolution in LedgerFlow
Money must never be created or lostDouble-entry ledger; DB triggers reject unbalanced or edited entries; long paise, no floats

Client retries charge twiceIdempotency-Key claimed with INSERT … ON CONFLICT DO NOTHING before any work

Merchant must hear about every eventTransactional outbox → SNS → SQS → HMAC-signed webhooks, exponential retries, DLQ
Books must match the bankNightly settlement CSV in S3 → automatic reconciliation report with 4 discrepancy types

Real-world scenario

Follow one ₹250 chai order at "Chai Point" (merchant fee 2%) through a bad day.

1

Customer pays, network flickers

Chai Point's backend calls POST /v1/payments with Idempotency-Key: order-42. The phone's network drops the response, so the app retries with the same key. LedgerFlow sees the key is already COMPLETED and replays the stored response with Idempotent-Replayed: true. One payment, not two.

2

The bank goes quiet

LedgerFlow asks the bank to collect. The bank takes the money but its response never arrives (a timeout). LedgerFlow retries twice; because the bank deduplicates by payment id, the retry returns the same collect instead of charging again. Still no definite answer, so the payment becomes PENDING_CONFIRMATION and the merchant gets a payment.pending_confirmation webhook.

3

The poller finds out

Five seconds later the status poller asks the bank "what happened to this payment?" The bank says approved, so the payment becomes AUTHORIZED and a payment.authorized webhook goes out. If the bank had said "never heard of it" after a 2-minute grace period, the payment would be FAILED instead.

4

Capture moves the money

Chai Point captures. In one database transaction: the payment becomes CAPTURED, a journal entry debits the customer ₹250, credits Chai Point ₹245 and credits the platform ₹5, and an outbox row is written. If the customer's balance were too low, the whole transaction would roll back with INSUFFICIENT_FUNDS.

5

The merchant's server is down

The payment.captured webhook gets a 503. SQS redelivers it after 10 s, 20 s, 40 s, 80 s. It succeeds on attempt 3. Had it failed 5 times, it would land in the dead-letter queue and a CloudWatch alarm would email the team.

6

Customer wants ₹100 back

A partial refund posts the mirror-image entry: Chai Point gives back ₹98, the platform gives back ₹2 of its fee, and the customer gets ₹100. Status becomes PARTIALLY_REFUNDED.

7

Midnight: does everything match?

At 00:30 IST the bank drops its settlement file into S3. LedgerFlow matches every row: this payment matches and becomes SETTLED. Elsewhere it finds one payment the bank listed twice, one with a different amount, one the bank has but LedgerFlow doesn't, and one LedgerFlow has but the bank doesn't. Operations staff see all of this at GET /v1/reconciliation/2026-10-27.

RuleMechanism
Journal is append-onlyBEFORE UPDATE OR DELETE / TRUNCATE triggers raise an error. Mistakes are fixed with reversal entries.
Every entry balancesDeferred constraint trigger: at COMMIT, each entry needs ≥ 2 lines and debits = credits
No customer overdraftCHECK (allow_negative OR balance >= 0)
Refunds ≤ amount, fee ≤ amountCHECK constraints on payment
Idempotent webhook consumerwebhook_delivery.event_id primary key

Journal entries: worked example

₹250 payment (25,000 paise), fee 2% (500 paise), then a ₹100 refund.

EntryAccountDebitCredit
CaptureCustomer25,000
Merchant receivable24,500
Platform fee500
RefundMerchant receivable9,800
Platform fee200
Customer10,000

Fee returned on a refund uses cumulative rounding: round(fee × refundedSoFar / amount) − round(fee × refundedBefore / amount). Any sequence of partial refunds therefore returns exactly the original fee. A jqwik property checks this.

Ledger posting algorithm (LedgerService.post)

1. Look up each account's posting rule (type, allow_negative). No lock.
2. Guarded accounts (customers): SELECT … FOR UPDATE ORDER BY id
   → apply lines in Java → InsufficientFundsException if balance < 0
3. INSERT journal_entry + journal_lines, flush
4. Unguarded accounts (merchant, fee, bank), in id order:
   UPDATE account SET balance = balance + :delta     ← atomic, no read, issued last
COMMIT → deferred trigger verifies debits = credits
  • No deadlocks: every transaction takes locks in the same global order.
  • Hot accounts: the platform-fee row is touched by every capture. Updating it last, without reading it, shrinks its lock hold time to "step 4 → COMMIT". Load testing showed this was the main bottleneck before.

Idempotency

flowchart TD
    A[POST with Idempotency-Key] --> B{"INSERT key ON CONFLICT DO NOTHING"}
    B -- inserted --> C[Run the action]
    C -- success --> D[Store status + body, COMPLETED] --> E[Return response]
    C -- exception --> F[Delete key so client can retry] --> G[Return error]
    B -- conflict --> H{Same request hash?}
    H -- no --> I[422 IDEMPOTENCY_KEY_REUSED]
    H -- yes --> J{Status}
    J -- IN_PROGRESS --> K[409 IDEMPOTENCY_KEY_IN_USE]
    J -- COMPLETED --> L[Replay stored response<br/>Idempotent-Replayed: true]

Keys are namespaced merchantId:key, hashed over method + path + the re-serialized parsed body, and expire after 24 h.

Webhooks

Header: X-LedgerFlow-Signature: t=<unix>,v1=hex(HMAC_SHA256(secret, t + "." + rawBody)), plus X-LedgerFlow-Event-Id and X-LedgerFlow-Event-Type. Retry timeline: attempt 1 → +10 s → 2 → +20 s → 3 → +40 s → 4 → +80 s → 5 → DLQ. The backoff is the SQS message's own visibility timeout, so there's no retry table and no scheduler.

Deployment status, and how to describe it. The AWS setup is fully written in Terraform (it passes terraform validate) and the CI pipeline has a deploy job ready for it, but it has never been applied: the always-on parts (ALB ~$18, Fargate ~$25, RDS ~$15, public IPv4 ~$14) come to about $70–80/month. An accurate way to say it: "The AWS infrastructure is all in Terraform and the pipeline deploys to ECS through OIDC. I run it locally against LocalStack, which exercises the same SNS, SQS, S3 and Secrets Manager APIs, rather than paying about $75 a month to keep it up." If you'd rather say "it was deployed", deploy it once for an hour (about $0.10), take screenshots of the dashboard, then run terraform destroy.

Scalability options

The API is stateless and every background job (relay, poller, webhooks, reconciliation) already shares work safely across instances (SKIP LOCKED, leases, SQS). So the first scaling step is just "more tasks"; after that, the database is the bottleneck.

TargetChanges
~1,000 payments/sECS auto-scaling on CPU / ALB requests per target; larger RDS instance with provisioned IOPS; RDS Proxy or PgBouncer so many tasks share few DB connections; Multi-AZ RDS for failover
~5,000/sRead replica for GETs and reports; partition journal_line, outbox_event, idempotency_key by time and drop old partitions instead of deleting; split the hot platform-fee account into N sub-accounts (pick one by hash) and sum them for reporting
Beyond one databaseShard by merchant (each shard its own Postgres; a payment never spans merchants); replace the polling relay with CDC (Debezium → Kafka)
OrderingSNS/SQS FIFO with MessageGroupId = paymentId, or Kafka partitioned by payment id, if consumers need strict per-payment order
Webhooks at scalePer-merchant concurrency limits and circuit breakers so one slow merchant can't starve others; separate queues for large merchants
Reconciliation at scaleStream the CSV instead of loading it; chunk by payment-id range; run on its own worker service
Multi-regionActive-passive: Aurora Global Database, Route 53 failover. Active-active for a ledger is hard (it needs a single writer per account).

Run the demo locally

About 15 minutes end to end. Commands are for Windows PowerShell, run from the repo root (D:\Ledgerflow).

Before the interview: start Docker Desktop, run step 1 once so images are built (the first build takes a few minutes), then leave the stack running. Have this page and Swagger UI open in tabs.

Prerequisites

Docker Desktop (running), Python 3 (for the tools), Git. Java 21 only if you want to run the tests (step 13). Ports 5432, 4566, 8080, 8081 and 9090 must be free.

Set up a session in PowerShell

$api   = "http://localhost:8080"
$token = (Invoke-RestMethod -Method Post "$api/dev/token?merchantId=11111111-1111-1111-1111-111111111111").access_token
$auth  = @{ Authorization = "Bearer $token" }
function Post($path, $body, $key = [guid]::NewGuid().ToString()) {
  Invoke-RestMethod -Method Post "$api$path" -Headers ($auth + @{ "Idempotency-Key" = $key }) -ContentType "application/json" -Body $body
}

The demo merchant "Chai Point Demo" (2% fee) and customers cust_alice, cust_bob (₹10,000 each) and cust_0001…cust_1000 (₹1,000 each) are seeded.

4

Create a payment

$p = Post "/v1/payments" '{"customerId":"cust_alice","amount":25000}' "demo-order-1"
$p

Amount is in paise (₹250). Status is usually AUTHORIZED. The bank is chaotic, so you may get PENDING_CONFIRMATION (great, see step 6) or FAILED (create another with a new key).

5

Prove idempotency

# same key, same body → same payment, replayed
$r = Invoke-WebRequest -UseBasicParsing -Method Post "$api/v1/payments" -Headers ($auth + @{ "Idempotency-Key" = "demo-order-1" }) -ContentType "application/json" -Body '{"customerId":"cust_alice","amount":25000}'
$r.Headers["Idempotent-Replayed"]; ($r.Content | ConvertFrom-Json).id

# same key, different body → 422
try { Post "/v1/payments" '{"customerId":"cust_alice","amount":999}' "demo-order-1" } catch { $_.Exception.Response.StatusCode.value__ }

Expect true and the same id as $p.id, then 422 (IDEMPOTENCY_KEY_REUSED).

Interview questions & answers

Click a question to open the answer. Answers are written the way you'd say them.

Q1Walk me through the architecture and the life of a payment.

Two Spring Boot services and Postgres, plus AWS messaging. A merchant calls POST /v1/payments with a JWT and an Idempotency-Key. LedgerFlow claims the key, inserts the payment as CREATED with an outbox event in one transaction, then calls the bank outside any transaction. A second short transaction records the answer: AUTHORIZED, FAILED or PENDING_CONFIRMATION. Capture is one transaction that changes the status, posts a balanced journal entry (customer debit, merchant and fee credits) and writes an outbox row. The outbox relay publishes events to SNS; SNS feeds an SQS queue; a dispatcher signs and POSTs webhooks with retries and a DLQ. Every night the bank writes a settlement file to S3, which triggers reconciliation through another SQS queue, and matched payments become SETTLED.

Q2Why double-entry, and how do you guarantee the books always balance?

Double-entry means every movement is recorded as equal debits and credits across accounts, so money can't appear or vanish: the sum over all lines is always zero. I enforce it at three levels:

  • The Java JournalEntryDraft builder refuses an unbalanced draft.
  • A deferred constraint trigger in Postgres checks at COMMIT that each entry has at least 2 lines and debits = credits, so even a bug or a manual SQL session can't commit an unbalanced entry.
  • Journal tables are append-only: triggers reject UPDATE, DELETE and TRUNCATE. Corrections are reversal entries, which keeps a full audit trail.

Account balances are a cached projection; tests run an independent SQL audit that recomputes every balance from the lines and checks for zero drift and zero global imbalance.

Q3Two captures hit the same customer at the same time. How do you stop an overdraft?

Customer accounts are "guarded". Inside the capture transaction I lock them with SELECT … FOR UPDATE, check the balance in Java and write it back. The second transaction blocks on the row lock until the first commits, then sees the reduced balance and fails with INSUFFICIENT_FUNDS. As a last line of defence the table has CHECK (allow_negative OR balance >= 0).

The test: fund one account for exactly 500 transfers and fire 1,000 concurrently. Exactly 500 succeed, 500 get insufficient funds, the balance ends at 0. If I remove the lock, the test fails: all 1,000 "succeed" because of lost updates. That proves the test really exercises the locking.

Why not optimistic locking (@Version)? With 1,000 writers on one row, almost everyone conflicts and retries, which becomes a retry storm. Pessimistic locking queues them instead.

Q4How do you avoid deadlocks?

A deadlock needs two transactions taking the same locks in opposite orders (A→B and B→A). I sort account ids and always lock guarded accounts in ascending id order, then update unguarded accounts in id order. With one global order there can't be a cycle. The test runs 1,000 random transfers in both directions across 5 accounts and asserts zero deadlock errors and an unchanged total.

Q5What is the "hot account" problem and how did you fix it?

Every capture credits the same platform-fee account and the same merchant account. Originally I locked them like customer accounts, for the whole transaction, so all captures for a merchant queued on one row. The k6 load test showed it as rising capture latency.

Those accounts may go negative, so there's nothing to check before writing. Now they get a single atomic UPDATE account SET balance = balance + :delta, issued last, just before COMMIT. Postgres still serializes writers on that row, but only for the moment between that statement and COMMIT. A test fires 1,000 concurrent credits at one such account and checks that all of them land. At larger scale, I'd split the fee account into N sub-accounts and pick one by hash.

Q6How does idempotency work? What about two identical requests at the exact same moment?

Before doing any work I run INSERT INTO idempotency_key … ON CONFLICT DO NOTHING with merchantId:key, a hash of the request and status IN_PROGRESS. The primary key is the lock: exactly one of two concurrent requests inserts the row.

  • The winner runs the action, then stores the status code and body as COMPLETED.
  • A loser that arrives while the winner is still running gets 409 IN_PROGRESS, and the client retries later.
  • A later request with the same body gets the stored response replayed, with Idempotent-Replayed: true.
  • The same key with a different body gets 422.

The hash covers the parsed and re-serialized body, so whitespace and key order don't matter.

If the action throws, the key is released so the client can retry. One subtlety: once the payment row exists, create always returns it even if a later step fails. Otherwise releasing the key could let a retry create a second payment. RetryStormIT fires 200 concurrent creates with one key and asserts exactly one payment.

Q7The bank call times out. Did the customer pay? What do you do?

A timeout means "unknown", not "failed": the bank may have collected and lost the response. So:

  1. Retry safely. Up to 2 retries with exponential backoff and jitter, only for timeouts and 5xx. It's safe only because the bank deduplicates by payment id; a retry gets the original result instead of a second charge.
  2. Admit uncertainty. Still unknown? The payment goes to PENDING_CONFIRMATION, and the merchant gets an event saying so.
  3. Follow up. A status poller asks the bank later, with per-payment exponential backoff. Approved → AUTHORIZED; declined → FAILED. "No record" counts only after a 2-minute grace, because a request may still be in flight.
  4. Bound it. After 30 minutes the payment fails with CONFIRMATION_TIMEOUT. If the bank had actually collected, the nightly reconciliation reports it as missing-in-ledger.

The chaos run sends 300 payments through a bank where about 1 in 4 calls misbehaves, then compares every final status with the bank's records: 0 mismatches.

Q8Why not do create + bank call + update in one transaction?

A transaction holds a database connection, and possibly row locks, for its whole duration. If the bank takes 10 seconds, every in-flight payment holds a connection for 10 seconds; with a pool of 30, the 31st request waits, and a slow bank takes the whole API down. So it's two short transactions with the network call between them. The trade-off is a crash window between them: the payment stays CREATED. That's covered because every new payment is scheduled for a status check after 1 minute as a safety net.

Q9What is the transactional outbox and why did you use it?

The dual-write problem: if I commit to Postgres and then publish to SNS, a crash between them loses the event; if I publish first and the transaction rolls back, I've announced something that didn't happen. With the outbox, the event is a row inserted in the same transaction as the state change, so both happen or neither does.

A relay then reads unpublished rows with FOR UPDATE SKIP LOCKED (several instances can relay in parallel without double-sending), publishes them in batches of 10 with SNS PublishBatch, and marks them published. A crash after publishing but before marking means the row is sent again, so delivery is at least once. Consumers deduplicate by event id; the webhook consumer uses event_id as a primary key.

Q10How do webhook retries and the dead-letter queue work?

The dispatcher consumes from SQS. On a non-2xx or a network error it sets that message's visibility timeout to the backoff (10 s, 20 s, 40 s, 80 s, capped at 5 min) and leaves it on the queue. SQS makes it visible again later: the queue itself is the retry scheduler, so there's no retry table and no cron. The queue's redrive policy moves the message to a DLQ after 5 receives, and a CloudWatch alarm fires when the DLQ isn't empty. Operators can fix the merchant's endpoint and redrive the DLQ.

The webhook_delivery table records attempts and status and skips events already delivered, which handles duplicates from SNS, SQS or the relay. With a merchant failing 30% of requests, 98.9% were delivered after retries, and 7 of 640 went to the DLQ.

Q11How does a merchant know a webhook really came from you?

Stripe-style signatures: X-LedgerFlow-Signature: t=<timestamp>,v1=HMAC-SHA256(secret, t + "." + rawBody).

  • The merchant recomputes the HMAC over the raw bytes and compares in constant time, which avoids timing attacks.
  • The timestamp is inside the signature, so the merchant can reject anything older than about 5 minutes. That stops replay attacks.

The secret lives in Secrets Manager and is cached for 5 minutes, so rotation needs no restart. I verified the scheme against an independent Python implementation (the demo merchant), which reported 0 bad signatures.

Q12Explain reconciliation. What edge cases did you handle?

The bank's settlement file is the external truth. I match both sides by payment id and report four discrepancy types:

  • Duplicate: the bank listed a payment twice.
  • Missing-in-ledger: the bank has it, LedgerFlow doesn't consider it collected (for example a payment we timed out but the bank collected).
  • Amount mismatch.
  • Missing-in-bank: we think it was collected, the bank doesn't list it.

Matched payments become SETTLED. The matching is a pure function with no I/O, so a jqwik property plants random mixes of all four kinds and asserts each is reported exactly, with nothing extra. Edge cases:

  • Business dates are IST.
  • A payment collected just before midnight that appears in the next day's file still matches by id.
  • A re-uploaded file produces a new report; the API serves the latest.
  • A file that can't be processed goes to a DLQ after 3 tries.

Measured: 40 of 40 planted mistakes caught, 0 false alarms.

Q13How do background jobs behave when you run several API instances?

No leader election is needed. Each job claims work with FOR UPDATE SKIP LOCKED: rows another instance has locked are skipped, not waited on, so instances naturally split the work. The status poller goes further: it claims rows by pushing next_status_check_at forward by a 1-minute lease in one auto-committed statement, then calls the bank holding no database lock. If that instance dies, the lease expires and another instance picks the payment up. SQS consumers are naturally competing consumers. Reconciliation uses one message at a time.

Q14How did you test all this? How do you know the tests are meaningful?
  • 65 unit tests for fee maths, hashing, signatures and the gateway's retry rules.
  • 9 jqwik property tests, each with up to 1,000 generated cases: the ledger always balances, refunds never exceed the capture and always return exactly the fee, random operation sequences respect the state machine, and reconciliation finds every planted discrepancy.
  • 44 integration tests with Testcontainers against real Postgres and LocalStack (no mocks of the database or AWS), plus scriptable fake bank and merchant servers.

Every integration test ends with an independent SQL audit. To make sure the concurrency tests have teeth, I removed the lock and watched them fail. On top of that: a chaos script, a reconciliation scorer and a k6 load test against the real Docker stack.

Q15What did the load test show, and what did you change because of it?

The k6 test runs create + capture at a constant arrival rate. The final result was 175 payments/s (347 req/s) for 2 minutes with 0 errors: create p99 66 ms, capture p99 180 ms, saturating around 190/s on a laptop. After about 520,000 journal lines: zero imbalance. Four bottlenecks were fixed along the way:

  1. Hot-account locks: fixed with atomic increments issued last.
  2. Connection pool waits: pool raised from 10 to 30.
  3. Outbox backlog: one SNS call per event replaced with PublishBatch.
  4. A sequential status poller: replaced with virtual-thread parallel checks that drain full batches.

The remaining limit is Postgres commit flushes inside Docker Desktop, i.e. disk fsync, not application code.

Q16How would you scale this to 10x or 100x?

10x: the API is stateless and the jobs already share work, so add ECS tasks with auto-scaling, use a bigger RDS instance, put RDS Proxy or PgBouncer in front so connections don't explode, and make RDS Multi-AZ.

100x:

  • Read replicas for GETs and reports.
  • Time-partition the journal, outbox and idempotency tables.
  • Split hot system accounts into sub-accounts.
  • Shard by merchant: a payment never spans merchants, so each shard is an independent Postgres.
  • Replace the polling outbox relay with CDC (Debezium → Kafka).
  • Give each merchant its own webhook concurrency limits.

The ledger's correctness model (row locks within one database) stays the same inside each shard, which is why merchant sharding is attractive.

Q17Why these AWS services? Walk me through the security setup.

Each service matches a need:

  • ECS Fargate: containers without managing servers.
  • RDS: managed Postgres, since the ledger depends on Postgres features.
  • SNS: fan-out of events.
  • SQS: durable queues with built-in retry timing and DLQs.
  • S3: files plus event notifications.
  • EventBridge Scheduler: a time-zone-aware cron.
  • Secrets Manager: keys and the database password.

Security:

  • RDS sits in private subnets with no internet route.
  • Tasks accept traffic only from the ALB's security group, and the bank only from the API.
  • Each service has its own IAM task role scoped to exact ARNs (for example, the API can only read settlements/* and write reports/*).
  • Secrets are injected from Secrets Manager at start-up, never baked into images.
  • GitHub deploys through OIDC: no stored AWS keys, and the role trusts only this repo's main branch.

I skipped the NAT gateway (about $35/month); the trade-off is that tasks need public IPs. HTTPS on the ALB needs a domain and an ACM certificate.

Q18Events can arrive out of order. Is that a problem?

Standard SNS and SQS don't guarantee order, and retries reorder further. So a merchant could see payment.captured before payment.authorized. Every event carries the full current status and an occurredAt timestamp, so a consumer can ignore events older than what it already has. If strict per-payment order were required, I'd use SNS FIFO + SQS FIFO with MessageGroupId = paymentId, accepting lower throughput. That's ordering per payment, not globally, which is all a merchant needs.

Q19Why store money as long paise? How are fees rounded?

Floating point can't represent 0.1 exactly, so sums drift. BigDecimal works but is slower and easy to misuse (scale, equals). Integer paise is exact and fast; the API caps amounts at ₹1 crore so amount × bps can't overflow, and Math.multiplyExact guards it anyway. Fees are integer basis points with half-up rounding.

For partial refunds, rounding each refund separately can leak a paisa. So I compute the cumulative fee returned after this refund minus what was already returned. Any split of refunds returns exactly the original fee, which is a jqwik property.

Q20What's missing for real production use? What would you do differently?
  • HTTPS on the ALB (needs a domain and an ACM certificate) and mTLS or signed requests to the bank.
  • Merchant onboarding and API-key management instead of seeded merchants.
  • Multi-AZ RDS with tested point-in-time restore.
  • Remote Terraform state (S3 with locking).
  • A durable bank simulator (mock-bank keeps its state in memory).
  • Rate limiting per merchant.
  • PII handling and encryption policies.
  • Distributed tracing (OpenTelemetry) across API, SQS and webhooks.
  • Runbooks for DLQ redrive.

Design-wise, at higher scale I'd move the outbox relay to CDC, and consider a FIFO or Kafka pipeline if merchants needed ordered events.
